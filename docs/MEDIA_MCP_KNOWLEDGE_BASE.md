# База знаний и архитектурный регламент video_pipeline (media_mcp)

Документ фиксирует проверенные на практике правила, математику латентов, особенности моделей Wan 2.2 и LTX-Video, а также антипаттерны (ошибки, которые категорически нельзя повторять).

> **Обязательное правило перед началом любых изменений конвейера генерации:**
> Всегда сверяться с этим документом. Если возникает проблема с латентами, цветом, стыками или перекрытием — решение уже исследовано и описано ниже.

## 1. Контракт латентного пространства ComfyUI (`process_latent_out` vs `process_latent_in`)

### Анатомия KSampler в ComfyUI
В ядре ComfyUI (`comfy/samplers.py`, строка 1238):
```python
samples = executor.execute(...)
return self.inner_model.process_latent_out(samples.to(torch.float32))
```
Где `self.inner_model.process_latent_out(latent)` вызывает (`comfy/model_base.py`, строка 383):
```python
return self.latent_format.process_out(latent)
```

### Формулы масштабирования Wan 2.1 / Wan 2.2 (`comfy/latent_formats.py`):
- **`process_in(latent)`** (из VAE в нормализованное диффузионное пространство):
  $$x_{\text{norm}} = \frac{x_{\text{vae}} - \mu}{\sigma} \times \text{scale\_factor}$$
- **`process_out(latent)`** (из диффузионного пространства обратно в сырое VAE):
  $$x_{\text{vae}} = x_{\text{norm}} \times \frac{\sigma}{\text{scale\_factor}} + \mu$$

Для Wan 2.1 VAE (16 каналов):
$\sigma \in [1.12, 3.27]$ (в среднем $\approx 2.1$), $\text{scale\_factor} = 1.0$.

### ⚠️ Критический капкан: Двойной вызов `process_out` (Double-Scaling Trap)
- Любой тензор `samples`, возвращаемый нодой `KSamplerAdvanced` (и сохраняемый нодой `SaveLatent` в `.latent`), **УЖЕ переведён в пространство сырого VAE**.
- **ЗАПРЕЩЕНО** вызывать `latent_format.process_out()` при загрузке `tail.latent` из файла:
  - Если вызвать `process_out` повторно, дисперсия умножается на $\sigma$ второй раз: $\text{std}$ подскакивает с $1.77$ до $4.15$, а диапазон значений раздувается с $[-5.5, 7.4]$ до $[-17.6, 20.9]$.
  - Внутри модели DiT (`model_base.py:1647`) на `concat_latent_image` вызывается `process_latent_in()` ровно один раз. Латенты заходят в сеть с утроенной амплитудой.
  - **Симптом ошибки:** Дикий пересвет, выбеливание цветов (RGB улетает в 200–235), потеря контраста и разрыв непрерывности префикса (MAE > 55).
- **Правильная реализация:**
  ```python
  # src_samples из SaveLatent УЖЕ находится в шкале VAE
  prefix_vae = src_samples
  concat_latent[:, :, :k_lat] = prefix_vae
  ```

## 2. Маскирование и кондиционирование в Wan 2.2 (`noise_mask` vs `concat_mask`)

### Архитектура Wan 2.2 I2V
Wan 2.2 — это Flow Matching модель (`ModelSamplingSD3`, `shift=5.0`).
Модель кондиционируется через входные каналы Patch Embedding (суммарно 36 каналов):
$$\text{Patch Input} = [\text{noise\_latents (16)}, \text{concat\_mask (4)}, \text{concat\_latent\_image (16)}]$$

### ⚠️ Критический капкан: Использование `noise_mask` в `out_latent`
- В ComfyUI при наличии ключа `noise_mask` в возвращаемом словаре латента сэмплер переключается в режим **`KSamplerX0Inpaint`**.
- В Flow Matching сэмплере стандартный инпейнтинг разрывает фазовые векторы на границе `mask = 0` (префикс) и `mask = 1` (ядро).
- **Симптом ошибки:** Изуродованный, грязный, выцветший первый кадр нового блока (обвал яркости на 65 пунктов, MSE > 12 000, эффект «испорченного кадра»).
- **Правильная реализация:**
  ```python
  # Никакого noise_mask! Только чистые нули под диффузию:
  out_latent = {
      "samples": torch.zeros([batch_size, 16, t_latents, h_lat, w_lat], device=device, dtype=torch.float32)
  }
  # Кондиционирование передается строго через positive/negative:
  pos_out = node_helpers.conditioning_set_values(positive, {"concat_latent_image": concat_latent, "concat_mask": mask})
  neg_out = node_helpers.conditioning_set_values(negative, {"concat_latent_image": concat_latent, "concat_mask": mask})
  ```

## 3. Заполнение будущих кадров в `concat_latent` (`ref_pad_image` Ghosting Trap)

### ⚠️ Критический капкан: Заполнение будущих кадров статичным изображением
- В ComfyUI нода `WanImageToVideo` имеет параметр `ref_pad_image`.
- **ЗАПРЕЩЕНО** дублировать опорный кадр (первый кадр выборки, anchor image) в паддинг будущих кадров `concat_latent[k_lat:]`!
- **Симптом ошибки:** 3D Spatiotemporal Self-Attention модели DiT воспринимает повторяющийся в каждом кадре референс как статическое руководство. На всём протяжении ролика появляется полупрозрачный застывший «призрак» (ghosting / двойник) первого кадра.
- **Правильная реализация:**
  Будущие кадры ($t > k_{\text{lat}}$) в `concat_latent` должны заполняться **строго плоским серым цветом 0.5** (`vae.encode(torch.ones(...) * 0.5)`), как и обучалась оригинальная модель Wan 2.2 I2V:
  ```python
  gray_img = torch.ones((length, height, width, 3), device="cpu", dtype=torch.float32) * 0.5
  concat_latent = vae.encode(gray_img[:, :, :, :3]).to(device=device)
  concat_latent[:, :, :k_lat] = prefix_vae[:batch_size, :, :k_lat]
  ```

## 4. Временной шаг (Temporal Stride) и математика кадров

| Параметр | Wan 2.2 (14B) | LTX-Video (22B) |
| :--- | :--- | :--- |
| **Сжатие VAE по времени** | $4\times$ Causal 3D | $8\times$ 3D |
| **Формула числа кадров** | $T_{\text{pixel}} = 1 + 4(k_{\text{lat}} - 1)$ | $T_{\text{pixel}} = 1 + 8(k_{\text{lat}} - 1)$ |
| **Допустимые длины кадров** | 17, 33, 49, 65, 81, ... ($T \equiv 1 \pmod 4$) | 17, 25, 33, 41, 49, 65, 81 ($T \equiv 1 \pmod 8$) |
| **Каналы латента** | 16 | 128 |
| **Пространственное сжатие** | $8\times$ (832x480 -> 104x60) | $32\times$ |

### Расчёт латентов перекрытия (`overlap`) для Wan 2.2:
```python
overlap_pixels = max(1, int(round(overlap * fps)))
# Каждые 4 пиксельных кадра дают 1 дополнительный латент:
k_tail_lat = max(2, math.ceil((overlap_pixels - 1) / 4) + 1)
```
- Для `overlap = 1.0s` при 16 fps: `overlap_pixels = 16`, $k_{\text{tail\_lat}} = 5$ латентов (соответствует 17 пиксельным кадрам).
- Для `overlap = 1.5s` при 16 fps: `overlap_pixels = 24`, $k_{\text{tail\_lat}} = 7$ латентов (соответствует 25 пиксельным кадрам).

### Нарезка блоков:
- **Блок 1**: генерирует $T_{\text{core}} + 1$ кадров. Хвост отрезается нодой `LatentCut(dim="t", index=-k, amount=k)` от выхода сэмплера.
- **Блок $N$ ($N \ge 2$)**: генерирует $T_{\text{total}} = T_{\text{prefix}} + T_{\text{core}}$ кадров.
  - Кадры $[0 : T_{\text{prefix}}]$ отрезаются через `ImageFromBatch` $\to$ сохраняются в `{prefix_str}-prefix.mp4` (отладка).
  - Кадры $[T_{\text{prefix}} : T_{\text{total}}]$ отрезаются через `ImageFromBatch` $\to$ сохраняются в `{prefix_str}-core.mp4` (рабочий блок).

## 5. Чтение размерности латентов без PyTorch (`read_latent_temporal_frames`)

Чтобы избежать загрузки тяжёлого пакета `torch` в процесс MCP-сервера при расчёте временного сдвига $T_{\text{prefix}}$ из сохранённого файла `{prefix_str}-tail.latent`, модуль `src/core/lora_inspector.py` реализует функцию `read_latent_temporal_frames(path)`:
- Считывает 8-байтовый little-endian заголовок `.safetensors` и парсит JSON-метаданные тензора `samples` (`shape: [B, C, T, H, W]`).
- Извлекает координату $T = \text{shape}[2]$ напрямую через стандартные модули `struct` и `json` за $<0.1\text{ мс}$.

## 7. Физика расхождения префикса в KSampler (Ре-диффузия и 3D Causal VAE)

### А. Почему в стандартном KSampler префикс ре-диффузируется из шума
1. В стандартной схеме `out_latent = {"samples": torch.zeros(...)}` KSampler заполняет **все** кадры случайным белым шумом $\mathcal{N}(0, I)$ при $\sigma_{\max} = 1.0$.
2. Вход DiT (`patch_embedding`) состоит из 36 каналов:
   - 16 каналов: диффузионные зашумленные латенты $x_t$ (включая кадры префикса).
   - 4 канала: `concat_mask` (0 для префикса, 1 для новых кадров).
   - 16 каналов: `concat_latent_image` (чистый латент префикса).
3. **Проблема:** Wan 2.2 I2V обучался на кондиционировании **только по 1 опорному кадру** ($t=0$). Архитектура DiT не умеет «замораживать» латенты: она реконструирует все 5 кадров префикса из белого шума шаг за шагом под управлением перекрестного внимания нового текстового промпта.
4. **Следствие:** На шаге 20/30 восстановленный префикс неизбежно накапливает остаточный шум и смещение стиля/движения в сторону нового промпта, теряя побитовое совпадение с исходным `tail.latent`.

### Б. Почему первый кадр префикса кажется интерлейсным / гребёнчатым (3D Causal VAE Phase Distortion)
1. VAE в Wan 2.2 использует причинно-следственные (Causal) 3D свертки с $4\times$ сжатием по времени.
2. При декодировании последовательности с начала ($t=0$) у VAE отсутствует предшествующий временной контекст («zero-history condition»).
3. Это порождает фазовое запаздывание на нечётных и чётных строках (эффект чересстрочной гребёнки / interlaced shift) именно на первом кадре.
4. В оригинальном Блоке 1 кадры хвоста декодировались в конце длинного контекста ($t = 44 \dots 60$), поэтому фазовых искажений там нет.
5. При сборке видео через FFmpeg кадры префикса Блока 2 отрезаются, а кадры `core` начинаются с $t \ge 16$, где временной контекст VAE уже полностью сформирован.

## 8. Архитектура бесшовной непрерывности: Вариант Б (Native Diffusion Forcing)

### Сравнение подходов: Вариант А vs Вариант Б

| Критерий | Вариант А (`KSamplerX0Inpaint` / `noise_mask`) | Вариант Б (Native In-Sampler Diffusion Forcing) |
| :--- | :--- | :--- |
| **Принцип** | На каждом шаге замешивает чистый латент без шума ($\sigma=0$) в замаскированную область. | Фиксирует предсказанный вектор чистого латента ($x_0$) через хук сэмплера `sampler_post_cfg_function`. |
| **Уровень шума на стыке** | Разрыв: в префиксе $\sigma=0$, в ядре $\sigma=t$. | Полная гармония: и префикс, и ядро находятся на одинаковом уровне шума $\sigma(t)$. |
| **Поведение Flow Matching** | Взрыв градиентов скорости на границе маски, деградация фаз. | Идеально гладкая прямая траектория $x(t) = \sigma(t)\epsilon + (1 - \sigma(t))x_0$. |
| **Результат** | Грязный, выцветший первый кадр ядра (MSE > 12 000, $\Delta\text{RGB} > 60$). | Бесшовное продолжение без артефактов (MSE < 2 000, $\text{MAE} < 10$). |

### Устройство нод Варианта Б в `ComfyUI-MediaMCP`:

1. **`WanLatentPrefixLock`** (Model Patch Node):
   - Принимает `model` (`MODEL`) и `prefix_latent` (`LATENT`).
   - Переводит `prefix_latent` в нормализованное диффузионное пространство модели через `model.process_latent_in()`.
   - Регистрирует хук `sampler_post_cfg_function`:
     ```python
     def prefix_clamp_hook(args):
         denoised = args["denoised"] # вектор x_0
         k = min(prefix_norm.shape[2], denoised.shape[2])
         denoised = denoised.clone()
         denoised[:, :, :k] = prefix_norm[:, :, :k].to(denoised.device, denoised.dtype)
         return denoised
     ```
   - За счёт этого метод Эйлера на каждом шаге вычисляет шаг $d = (x - x_0) / \sigma$ строго по направлению к `prefix_norm`. Текстовый промпт нового блока не может сместить префикс, а DiT-внимание ядра получает идеальный неискаженный контекст.
2. **Двухступенчатый Графовый Latent AdaIN (`LatentCut` + `LTXVAdainLatent` + `LatentConcat`) и `WanLatentPrefixRestore`**:
   - В `wan-fast` 4-шаговая дистилляционная LoRA (`wan2.2_i2v_lightx2v_4steps_lora_v1_high_noise`) на этапе `sampler_stage1` (шаги 0–2) сдвигает поканальные средние генерируемых кадров ядра ($t \ge k_{\text{lat}}$) по каналам 5, 6, 8, 9 ($\Delta\mu \approx \pm 1.17$) и раздувает дисперсию в $1.31\times$.
   - Чтобы этот сдвиг не запекался во втором сэмплере (`sampler_stage2`, Low-Noise UNet) и работал даже без перезапуска ComfyUI, граф выполняет поканальный **Latent AdaIN дважды** через нативные ноды `LatentCut` + `LTXVAdainLatent` + `LatentConcat`:
     1. **Между `sampler_stage1` и `sampler_stage2`** (на уровне шума $\sigma(\text{split\_step})$): ядро `stage1_cut_core` ($t \ge k_{\text{lat}}$) выравнивается по префиксу `stage1_cut_prefix` ($t < k_{\text{lat}}$).
     2. **После `sampler_stage2` перед `VAEDecode`**: чистое ядро `stage2_cut_core` выравнивается по эталонному `load_prefix_latent`, склеивается с `load_prefix_latent` через `LatentConcat` и проходит через `WanLatentPrefixRestore`:
        $$\hat{s}_{:,:,k:} = \frac{s_{:,:,k:} - \mu_{\text{core}}}{\sigma_{\text{core}}} \cdot \sigma_{\text{pref}} + \mu_{\text{pref}}$$
   - **Отбор хвостового латента (`cut_tail_latent`):**
     Нода `LatentCut` берёт сэмплы строго **после** нормализации (`latent_for_decode`), гарантируя, что сохранённый `*-tail.latent` передаётся в следующий блок со 100% сохранением цветового профиля сцены.

### В. Архитектура 5D-латентного префикса в LTX-2.3: `LTXVAddLatentGuide` + `LTXVCropGuides` + `LTXVAdainLatent` (и каузальная асимметрия $t=0$)
1. **Каузальная асимметрия слота $t=0$ в LTX-2.3 (`CausalVideoAutoencoder` и `LTXVModel`):**
   - В LTX-2.3 **первый латентный кадр ($t=0$) кодирует ровно 1 пиксельный кадр ($[0, 1)$)** (в энкодере `SpaceToDepthDownsample` действует `pad_first=True`, дублирующий кадр 0 восемь раз; в декодере `DepthToSpaceUpsample` действует `drop_first_conv=True`, отбрасывающий 7 из 8 подкадров; а в DiT `LTXVModel` к токенам с `temporal_start == 0` прибавляется `keyframes_abs_pos_embedding`).
   - Все последующие латентные кадры ($t \ge 1$) кодируют **по 8 движущихся пиксельных кадров** ($[1, 9), [9, 17), \dots$).
   - Поэтому **ЗАПРЕЩЕНО** перезаписывать слот $t=0$ выхода `LTXVCropGuides` сырым хвостовым латентом предыдущего блока через `WanLatentPrefixRestore`: хвостовой латент $t=4$ Блока 1 является 8-кадровым латентом движения, и его принудительная подстановка в 1-кадровый слот $t=0$ ломает каузальный буфер `CausalVideoAutoencoder.Decoder` и создаёт скачок на стыке.
   - **Правильная цепочка для LTX (`overlap > 0`):** `LoadLatent` $\to$ `LTXVAddLatentGuide(latent_idx=0, strength=1.0)` $\to$ `SamplerCustomAdvanced` (при этом `LTXVScheduler` принимает чистый `empty_latent` для расчёта числа токенов) $\to$ `LTXVCropGuides` $\to$ `LTXVAdainLatent(reference=load_prefix_latent, factor=1.0)` $\to$ `VAEDecode`.
2. **Согласование `distilled-lora` и `CFGGuider` в LTX-2.3:**
   - В официальном пайплайне Lightricks LTX-2.3 (`LTX-2.3_T2V_I2V_Single_Stage_Distilled_Full.json`) при полном сэмплинге (`steps = 15..20`, `CFG = 3.0`) дистиллированная LoRA (`ltx-2.3-22b-distilled-lora-1.1`) подключается со **слабой силой `strength_model = 0.2`**, тогда как `strength_model = 0.7..1.0` предназначена для быстрого дистиллированного режима с `CFG = 1.0` (сэмплер `euler_ancestral`, 25 шагов). Использование `strength_model = 1.0` одновременно с `CFG = 3.0` на 20 шагах приводит к тройному переусилению градиентов скорости (эффект «странной/пережаренной» генерации).
   - Нативная частота кадров LTX-2.3 составляет **24 fps** (`default_fps = 24`), а при `default_fps = 16` в сценариях движение сохраняется плавным с шагом темпорального сжатия $8\times$.
3. **Режим 1-кадрового I2V в LTX-2.3 (`overlap: 0.0`): `LTXVPreprocess` + `LTXVImgToVideoInplace(0.9)` + `euler_ancestral`:**
   - В отличие от прямого скармливания исходного PNG в базовые ноды, промышленный эталон (Lightricks / `audio_to_video`) использует связку:
     - `LTXVPreprocess(img_compression=33)`: JPEG-подобная частотная предобработка исходного изображения, фильтрующая субпиксельный сенсорный шум и высокочастотный дрейф, на который 3D VAE реагирует появлением микросетки.
     - `LTXVImgToVideoInplace(strength=0.9)`: задаёт силу наложения опорного кадра 90%, оставляя 10% стохастического шума. Это принципиально предотвращает эффект «застывшего стартового кадра» (rigid frame freeze), позволяя модели свободно и плавно начать движение с первого же кадра.
     - Дистиллированный профиль (`cfg: 1.0`, `steps: 25`, сэмплер `euler_ancestral`, LoRA `strength_model = 0.7`) гарантирует естественную динамику камеры и персонажа без артефактов перегиба.

## 9. Динамика стыка блоков: "Prompt Shock" и Temporal CFG Ramp-Up

### Проблема: Скачок движения и размытие на первом кадре нового блока (Frame 17)
После внедрения Варианта Б префикс совпадает с хвостом Блока 1 бит-в-бит ($\text{MAE} = 6.72$).
Однако на первом же незафиксированном кадре нового блока (кадр 17, $t = k_{\text{lat}}$) возникал визуальный скачок ("prompt shock") и размытие движения (motion blur):
- **Причина:** На префиксных кадрах ($t < k_{\text{lat}}$) латенты удерживаются в исходной позе.
- На первом свободном кадре ($t = k_{\text{lat}}$) классификаторное руководство (Classifier-Free Guidance, CFG = 6.0) мгновенно прикладывает к диффузионному потоку 6-кратную силу нового текстового промпта:
  $$v_{\text{cfg}} = v_{\text{uncond}} + s \cdot (v_{\text{cond}} - v_{\text{uncond}})$$
- Вектор $s \cdot (v_{\text{cond}} - v_{\text{uncond}})$ превосходит физическую инерцию временного внимания (temporal self-attention), вызывая мгновенный неестественный рывок геометрии и высокочастотный сдвиг фаз.

### Анализ стандартных нод ComfyUI: почему они не подходят
1. **`VideoLinearCFGGuidance` (`comfy_extras/nodes_video_model.py`):**
   - **Архитектурное несоответствие размерностей (4D vs 5D):** Нода создана в 2023 году для Stable Video Diffusion (SVD), где кадры видео упаковывались в Batch-размерность: `[B*F, C, H, W]`. Она вычисляет:
     `scale = torch.linspace(min_cfg, cond_scale, cond.shape[0])`
     В современных 3D DiT (Wan 2.1/2.2, CogVideo, LTX) видео представлено 5D-тензором `[B, C, T, H, W]`, где `cond.shape[0] == 1` (батч), а время находится в `dim=2` (`T`).
     В результате `cond.shape[0] == 1` сводит `linspace` к скаляру `[min_cfg]`, а 4D-тензор `[1, 1, 1, 1]` либо вызывает ошибку бродкастинга, либо превращается в плоский статичный CFG по всему видео. Нода **физически не способна управлять временем $T$ в 5D-тензорах**.
   - **Глобальный vs Локальный разгон:** Даже при исправлении размерности `VideoLinearCFGGuidance` растягивает разгон на всё 5-секундное видео от 0 до $N$. На 3-й секунде CFG будет лишь ~3.5, а 6.0 достигнет только на самом последнем кадре, что убивает выразительность движения в основном теле блока.
   - **Отсутствие информации о префиксе:** Нода не знает границу префикса $k_{\text{lat}}$.

2. **`ConditioningSetAreaPercentageVideo`:**
   - Ограничивает область применения текстовых токенов перекрестного внимания через пространственно-временные боксы.
   - В 3D DiT полнокадровое внимание на жестких границах порождает ступени и фазовые артефакты, не обеспечивая плавного математического масштабирования вектора скорости.

### Решение: Встроенный Temporal CFG Ramp-Up в `WanLatentPrefixLock`
В ноду `WanLatentPrefixLock` интегрирован специализированный хук `sampler_cfg_function`:
1. Формирует 5D-тензор масштабирования `scale` формы `[1, 1, T, 1, 1]`, полностью согласованный с латентом `[B, C, T, H, W]`.
2. **Зона префикса ($0 \le t < k_{\text{lat}}$):** `scale = min_cfg = 1.0`. Текстовый промпт нового блока не имеет права прикладывать силу к зафиксированным кадрам.
3. **Зона рампы ($k_{\text{lat}} \le t < k_{\text{lat}} + N_{\text{ramp}}$):** `scale` плавно линейно нарастает от `min_cfg` (1.0) до целевого `cond_scale` (6.0) за $N_{\text{ramp}} = 2 \dots 3$ латента (8–12 видеокадров, ~0.5–0.75с).
4. **Зона основного действия ($t \ge k_{\text{lat}} + N_{\text{ramp}}$):** `scale = cond_scale` (100% мощности промпта до конца блока).

**Физический эффект:**
На кадре 17 ($t = k_{\text{lat}}$) CFG равен 1.0 (естественный нескорректированный диффузионный поток модели). Временное внимание от кадра 16 доминирует и сохраняет непрерывность персонажа, а ускорение движения начинается плавно и без размытия.

## 10. Гибридная архитектура стыковки: 1-кадровый I2V (`overlap: 0`) vs Латентный префикс (`overlap > 0`)

### Концепция разделения:
* **`overlap == 0` (или не задан, по умолчанию):** Продакшн-режим покадрового Image-to-Video чейнинга. Гарантирует абсолютную чистоту картинки без фазовых артефактов, шума и сеток 3D VAE.
* **`overlap > 0` (экспериментальный режим):** Латентный префикс для медленных/статичных сцен, где требуется непрерывность траектории оптического потока.

### Архитектура 1-кадрового I2V-чейннинга:
1. **Экспорт хвоста текущего блока напрямую из Workflow:**
   - Если `overlap == 0`, в воркфлоу ComfyUI автоматически добавляются ноды `ImageFromBatch` (выбирающая последний кадр $T-1$) и `SaveImage`:
     ```python
     wf["slice_tail_image"] = ImageFromBatch(image=vae_decode, batch_index=num_frames - 1, length=1)
     wf["save_tail_image"] = SaveImage(images=slice_tail_image, filename_prefix=f"{prefix_str}_tail")
     ```
   - **Почему это критически важно:** Кадр сохраняется в PNG **напрямую из несжатого float32 RGB тензора VAE**. Если бы мы извлекали его через FFmpeg из уже готового `video.mp4`, кадр прошел бы через H.264 сжатие с квантованием DCT и цветовой субдискретизацией **YUV 4:2:0** (потеря 75% цветового разрешения), а VAE следующего блока повторно закодировал бы артефакты компрессии в латенты.
   - FFmpeg извлечение сохраняется лишь как резервный fallback на случай отсутствия ноды `SaveImage`.
   - Запоминается как `next_tail_image`. Файл `next_tail_latent` очищается.
2. **Входная эстафета следующего блока:**
   - Следующий блок видит наличие `next_tail_image` и подключает нативный `WanImageToVideo` (или `LTXVImageToVideo`), где входным изображением служит `next_tail_image`.
   - Диффузится полная последовательность $T_{\text{total}} = 4 \times k_{\text{core}} + 1$.
3. **⚠️ Правило дедупликации стыковочного кадра (Исключение 1-Frame Freeze):**
   - Кадр 0 нового блока визуально тождественен последнему кадру предыдущего блока.
   - Чтобы избежать эффекта дублирования кадра (микро-зависания на 1/16 с при склейке `-c copy`), ядро видео `core` нарезается со смещением на 1 кадр:
     ```python
     slice_batch_idx = 1 # отсекаем кадр 0
     core_frames = 4 * k_core
     wf["slice_core"] = ImageFromBatch(image=vae_decode, batch_index=1, length=core_frames)
     ```
   - В результирующий блок входят только вновь сгенерированные кадры $1 \dots T$, обеспечивая бесшовное и непрерывное воспроизведение.
4. **Почему 1-кадровый I2V чист от деконволюционного муара:**
   - Декодер 3D Causal VAE в новом блоке декодирует видео как цельный массив с нуля ($t=0$), заполняя свой собственный внутренний кэш признаков `feat_map`.
   - В латентах нет искусственной склейки двух разных диффузионных траекторий, поэтому интерференция на субпиксельных свертках физически невозможна.

## 11. Дефект 12: Дрейф в фотореализм в LTX-2.3 при многоблочной генерации и эвристики стилевого якорения

### Симптом:
При генерации многоблочного сценария в `overlap: 0` (Mode B) или `overlap > 0` (Mode A) на движке `ltx`, где опорный кадр сцены выполнен в нефотореалистичном стиле (аниме, 2D-рисунок, 3D CGI), к 3-му блоку (6–9 секунда) изображение персонажа и окружения плавно превращается в реалистичную съемку живого человека без резких монтажных скачков. При этом на `wan-fast` подобного эффекта не наблюдается.

### Математическая и архитектурная первопричина:
1. **Различие механизмов Image Conditioning (Wan vs. LTX):**
   - **Wan 2.2 I2V:** использует визуальный кросс-аттеншн (CLIP/UMT5 vision embeddings), который непрерывно проецирует семантические признаки опорного изображения на каждый слой внимания DiT на всех шагах диффузии. Датасет обучения Wan также содержит разнообразные анимационные стили.
   - **LTX-2.3 22B:** не имеет отдельного кросс-аттеншна на картинку. Исходный кадр кодируется 3D VAE в единичный каузальный токен $t=0$, который подаётся в поток токенов DiT. Все последующие токены $t \ge 1$ управляются каузальным самовниманием и текстовым эмбеддингом.
2. **Доминантный prior датасета LTX-2.3:**
   - Модель LTX-2.3 обучалась практически исключительно на фотореалистичном видеоматериале.
   - Если в `video.prompt` и в `prompt` блоков отсутствуют ключевые слова стиля (`source_anime`, `anime style`, `cel shaded`, `illustration`), каузальное самовнимание за 6–9 секунд естественным образом угасает по отношению к токену $t=0$, и генерация регрессирует к базовому приоре модели — фотореализму живого человека.
3. **Почему нет скачков на стыках:**
   - В Mode B входной кадр каждого блока ($t=0$) в точности равен финальному кадру предыдущего блока (`-tail.png`). Пространственная непрерывность сохраняется идеально, поэтому стилевой дрейф происходит непрерывно кадр за кадром.

### Решение и эвристика:
- Использовать глобальные поля `video.prompt` и `video.negative_prompt` в `schemas/scenario.json`.
- Для стилизованных сценариев в LTX **обязательно** задавать в `video.prompt` токены стиля (например, `"source_anime, anime style, 2d cartoon illustration"`), а в `video.negative_prompt` — анти-токены (`"photorealistic, real life, 3d render, photo, realistic skin texture"`).

## 12. Дефект 13: Накопление генеративной энтропии, «звёздочки» и оплывание форм при длинных цепочках блоков (>4 блоков)

### Симптом:
В длинных непрерывных сценариях одной сцены ($N \ge 6\dots 10$ блоков по 2 секунды) на движке `wan-fast` или `ltx` к 4–5 блоку начинают появляться артефакты мелких структур (фаланги пальцев, черты лица оплывают), к 6–7 блоку возникают одиночные пиксельные искры («звёздочки»), а к 8–10 блоку накапливается сильная цветовая дисперсия вплоть до радужного клиппинга.

### Математическая первопричина:
1. **Эффект Марковской цепи в латентах ($8\times$ VAE сжатие):**
   Каждый последующий блок диффундирует от хвоста предыдущего ($B_{i-1} \to B_i$). В латентном пространстве ($H/8, W/8$) мелкие высокочастотные детали занимают всего 1–2 латентных ячейки. Каждый шаг генерации вносит крошечную погрешность дискретизации $\epsilon \approx 2\text{--}3\%$.
   Через 10 блоков дисперсия латентов возрастает более чем на $+17\%$ ($\sigma = 2.16 \to 2.34$), а пиковые значения латентов пробивают порог $|z| > 10.0$ ($z_{\text{max}} = 11.13$).
2. **Клиппинг декодера 3D VAE:**
   При $|z| > 10.0$ свёрточные слои и GroupNorm декодера VAE упираются в границу динамического диапазона, вызывая изолированные субпиксели максимальной яркости («звёздочки») и градиентный клиппинг RGB.
3. **Почему `ref_pad_image` запрещён (Ghosting Trap):**
   Попытка скормить модели исходный `anchor_image` в паддинг будущих кадров (`concat_latent[k_lat:]`) приводит к блокировке 3D Spatiotemporal Self-Attention и порождает застывший полупрозрачный силуэт-призрак первого кадра поверх движения. Паддинг будущих кадров обязан оставаться серым 0.5.

### Архитектурное решение и правила продакшна:
1. **Лимит блоков в сцене: максимум 2–3 блока (6–10 секунд непрерывного плана).** Непрерывный латентный чейнинг физически ограничен пределом накопления энтропии.
2. **Длинный метр (15–60+ секунд) строится через массив монтажных сцен (`scenes[]`):**
   Каждая новая сцена генерирует свой чистый опорный кадр `anchor_image` (общий план $\to$ средний план со спины $\to$ крупный план), что **полностью сбрасывает счетчик деградации в 0**. Все сцены соединяются без перекодирования через `ffmpeg -c copy`.
3. **Оптимальная длительность блока: 3.0–4.0 секунды.** Это даёт модели 48–56 свободных кадров для раскатистой инерции и вдвое сокращает количество склеек на один и тот же хронометраж.
4. **Учёт нативного обучающего горизонта модели (Wan vs LTX):**
   - **Wan 2.2:** Обучалась на фиксированных клипах по 81 кадру ($5.06$с при 16 fps). При превышении 81 кадра (например, попытка генерировать блок в 10 секунд = 161 кадр) механизм RoPE входит в зону нетренированной экстраполяции, что разрушает детализацию уже к 6-й секунде. Блоки Wan 2.2 обязаны быть $\le 5.0$с.
   - **LTX-2.3:** За счёт агрессивного $8\times$ темпорального VAE-сжатия (1 секунда при 16 fps = всего 2 латентных среза; 12 секунд = лишь 25 латентов) модель легко удерживает временной контекст на длинных интервалах (6–12 секунд на один блок). Для длинных непрерывных планов без склеек следует предпочитать LTX-2.3.

## 13. Математика латентов двустороннего кондиционирования (First-Last Frame Conditioning) и runtime-ссылки

При интерполяции между опорным кадром и конечным кадром блока (`end_image`) критично сохранять математическую структуру скрытого пространства модели:

### 1. Wan 2.2: 4-канальная суб-фрейм маска латентов
- Временной шаг VAE в Wan 2.2 составляет 4 кадра:
  $$T_{\text{pixel}} = 1 + 4 \times k_{\text{lat}}$$
- Для режима 1-кадрового I2V (`overlap == 0`) используется специализированная нода `WanFirstLastFrameToVideo`, принимающая пиксельные `image` и `end_image`.
- Для 5D латентного префикса (`overlap > 0`) нода `WanLatentPrefixToVideo` принимает оба кадра:
  1. Стартовый префикс кодируется в первые $k_{\text{pref}}$ срезов $5D$-латентов `[B, 16, T_lat, H_lat, W_lat]`.
  2. Конечный кадр `end_image` масштабируется фильтром Lanczos и помещается в последний срез пиксельной подложки:
     $$\texttt{gray\_img}[-\text{end\_img.shape}[0]:] = \text{end\_img}$$
  3. Маска кондиционирования Wan 2.2 имеет форму `[B, 4, T_lat, H_lat, W_lat]`. Для конечного кадра временной срез маски принудительно обнуляется:
     $$\texttt{mask}[:, :, -\text{end\_img.shape}[0]:] = 0.0$$
     Это сообщает сэмплеру DiT, что последний кадр жестко задан и не должен зашумляться, обеспечивая плавную интерполяцию промежуточных кадров к заданной позе/композиции.

### 2. LTX-2.3: Токенизированные направляющие (Token Guides) и изоляция шедулера
- В LTX-Video conditioning первого и последнего кадров реализуется через добавление служебных токенов в латентную последовательность:
  1. Пиксельные `start_image` и `end_image` сжимаются нодой `LTXVPreprocess` (`img_compression=25`).
  2. Ноды `LTXVAddGuide(frame_idx=0, strength=0.7)` и `LTXVAddGuide(frame_idx=-1, strength=0.7)` добавляют токены направляющих в конец латентной последовательности `active_latent_node` (оставляя 30% свободы адаптации для плавного морфинга геометрии/освещения) при использовании стохастического сэмплера `euler_ancestral`.
  3. **Изоляция шедулера:** вход `latent` ноды `LTXVScheduler` обязан оставаться подключенным к исходному чистому латенту (без токенов направляющих), чтобы не искажать расчет шагов шума.
  4. **Отрезка токенов (`LTXVCropGuides`):** перед декодированием через VAE и выравниванием AdaIN (`WanLatentPrefixRestore` / `LTXVAdainLatent`), добавленные токены направляющих обязательно отсекаются нодой `LTXVCropGuides`, возвращая тензор к размерности чистого видео.

### 3. Динамические runtime-ссылки `$start` и `$anchor` в `end_image`
В секции `end_image` блока поддерживаются семантические runtime-макросы:
- **`keyframe_path: "$anchor"`**: повторно использует исходный опорный кадр сцены напрямую без вызова генератора изображений (например, для цикличного возврата камеры или персонажа в исходную точку в финальном блоке сцены).
- **`keyframe_path: "$start"`**: использует стартовый кадр текущего блока как есть (опорный кадр сцены для блока 0, либо `-tail.png` предыдущего блока для блоков $N \ge 1$).
- **`image_path: "$anchor"` + `prompt`**: генерирует конечный кадр через img2img (`denoise: 0.55–0.65`) относительно исходного опорного кадра сцены.
- **`image_path: "$start"` + `prompt`**: генерирует конечный кадр через img2img относительно фактического старта текущего блока. Это ключевой приём для удержания фона, геометрии и ракурса камеры при локальном изменении позы/мимики персонажа.

#### Правила валидации и персистентности:
1. **Запрет в `scene.anchor_image`**: runtime-ссылки `$start` и `$anchor` запрещены в опорном кадре сцены (нельзя ссылаться на самого себя до инициализации сцены).
2. **Требование промпта для `image_path`**: ссылка в `image_path` обязана сопровождаться непустым `prompt`, поскольку img2img требует текстового описания желаемой трансформации.
3. **Сохранение неизменных литералов в `*-spec.json`**:
   - При сериализации спецификации сценария `*-spec.json` ссылки сохраняются строго как строковые литералы `"$start"` и `"$anchor"`, а не как абсолютные пути к временным файлам текущей сессии.
   - **Почему это критично:** Разворачивание ссылок в статические пути (`c:/.../block_0_tail.png`) навсегда привязало бы спецификацию к артефактам первого прогона. При повторном запуске или редактировании спецификации пайплайн подхватывал бы устаревшие изображения вместо актуальных кадров новой генерации.
4. **Контракт сохранения хвостовых кадров (`-tail.png`):**
   - Для всех нефинальных блоков сценария (`save_tail_image = not is_last`) воркфлоу ComfyUI **обязан сохранять** несжатый пиксельный кадр `{prefix_str}_tail.png` через связку `ImageFromBatch(batch_index=num_frames - 1, length=1)` + `SaveImage` напрямую из `vae_decode`.
   - Это выполняется как при `overlap == 0.0`, так и при `overlap > 0.0` (где параллельно сохраняется 5D латент `{prefix_str}_tail.latent` для чейнинга).
   - **Почему запрещено передекодировать `-tail.png` из `tail.latent` задним числом:**
     Декодирование полного видео в воркфлоу блока происходит с полным 3D темпоральным контекстом causal VAE, поэтому последний кадр свободен от фазовых искажений. Если же попытаться декодировать изолированный латент хвоста `tail.latent` отдельным вызовом VAE, Causal 3D VAE воспримет его как первый кадр без предыстории (`zero-history`), что приведёт к фазовой гребёнке и цветовому сдвигу.

## 14. Дефект 14: Фазовое зашумление и dissolve-эффект при First-Last Frame кондиционировании в LTX-2.3 vs Wan 2.2

### Симптом:
При генерации блока с заданным `end_image` в LTX-2.3 (через ноду `LTXVAddGuide`) в середине таймлайна (в районе 1.5–2 секунды при длительности блока 3–4 секунды) видео не переходит плавно в конечную позу, а проходит через выраженный фазовый артефакт: черты лица, глаза, руки или предметы на доли секунды растворяются в диффузионном шуме ("dream-like cross-dissolve" / кашеобразное зашумление), после чего материализуются в целевую композицию `end_image`. Если `end_image` был синтезирован через чистый `txt2img` без удержания геометрии окружения, переход выглядит для зрителя как резкий монтажный скачок (scene cut) посреди единого плана.

### Математическая и архитектурная причина (Token Guides vs Concat Inpainting):

```
+-------------------------------------------------------------------------------------------------+
|                                    Wan 2.2 Inpainting DiT                                       |
|                                                                                                 |
| Patch Input (36 ch):                                                                            |
| [ Noisy Latents (16 ch) | Binary Mask (4 ch) | Concat Latents (16 ch) ]                         |
|   t=0: mask=0, Start VAE                       t=T: mask=0, End VAE                             |
|   t=1..T-1: mask=1, Gray Pad                   t=1..T-1: mask=1, Denoising Canvas               |
|                                                                                                 |
| -> Непрерывный оптический поток (True Optical Flow & Dense Morphing)                            |
+-------------------------------------------------------------------------------------------------+

+-------------------------------------------------------------------------------------------------+
|                                    LTX-2.3 Causal DiT                                           |
|                                                                                                 |
| Denoising Canvas: [ 100% White Gaussian Noise N(0, I) across all frames t=0..T ]                |
| Appended Guides:  [ ... | Guide Token t=0 (strength 0.7) | Guide Token t=T (strength 0.7) ]     |
|                                                                                                 |
| -> Временное самовнимание в t=T/2 испытывает фазовое взаимное гашение (Phase Cancellation)     |
| -> Растворение промежуточных структур в стохастическом диффузионном шуме                        |
+-------------------------------------------------------------------------------------------------+
```

1. **LTX-2.3 — Causal Unidirectional DiT с токенизированными направляющими:**
   - Модель LTX-2.3 является строго однонаправленной (каузальной) моделью диффузии, обученной генерировать поток кадров слева направо ($t = 0 \to t = T$).
   - Нода `LTXVAddGuide` **не запекает** конечное изображение в диффузионный холст латентов! Канвас латентов промежуточных кадров остаётся 100% случайным белым шумом ($\sigma = 1.0$).
   - Направляющие кадры добавляются как служебные токены-ориентиры в конец последовательности с временными метками `temporal_coords`.
   - В процессе сэмплирования промежуточные латенты ($t \approx T/2$) испытывают взаимно противоположное тяготение к начальному токену $t=0$ и конечному токену $t=T$ через механизм 3D Self-Attention.
   - При малейшем геометрическом или композиционном расхождении между началом и концом фазовые векторы скорости $\mathbf{v}_{\text{start}}$ и $\mathbf{v}_{\text{end}}$ входят в противоречие (phase cancellation): модель не имеет плотной обучающей траектории двунаправленного связывания, и промежуточные кадры на 2-й секунде коллапсируют в диффузионный шум, создавая эффект "растворения через шум" (dissolve).
2. **Wan 2.2 — Native Inpainting с 36-канальным Patch Embedding:**
   - Wan 2.2 I2V изначально обучена с 36-канальным входным тензором: 16 шумных латентов + 4 канала бинарной маски + 16 каналов латентов conditioning-изображения.
   - Нода `WanFirstLastFrameToVideo` (и `WanLatentPrefixToVideo`) физически упаковывает и начальный ($t=0$), и конечный ($t=T-1$) кадры прямо в тензор `concat_latent` с нулевой маской (`concat_mask = 0`).
   - DiT обучен решать классическую задачу пространственно-временного заполнения (spatiotemporal inpainting). Внимание трансформера опирается на физические координаты пикселей обоих кадров на каждом слое сети, строя непрерывный оптический поток и плавную деформацию геометрии без провала в шум.

### Инженерные правила и матрица выбора движков (Decision Matrix):

| Сценарий задачи | Рекомендуемый движок | Архитектурная конфигурация | Почему именно так |
| :--- | :--- | :--- | :--- |
| **Жесткая интерполяция позы / ракурса (`end_image` задан)** | **Wan 2.2** (`wan-fast`, `wan-2.2`) | `WanFirstLastFrameToVideo` / `WanLatentPrefixToVideo` | Нативный 36-канальный inpainting. Гарантирует честный оптический морфинг без зашумления и скачков. |
| **Качественный непрерывный I2V план (без `end_image`)** | **LTX-2.3** (`ltx`) | 1-Frame I2V (`overlap: 0.0`), `cfg: 3.0`, `steps: 25`, `euler_ancestral`, LoRA `0.2` | Превосходит Wan по естественности физики, дыханию, микромимике глаз и плавности движения камеры на отрезках 6–12с. |
| **LTX-2.3 с вынужденным `end_image`** | **LTX-2.3** (`ltx`) | `"image_path": "$start"`, `denoise: 0.55–0.65`, `strength: 0.7`, `euler_ancestral`, `cfg: 3.0` | Строго img2img от старта блока. Категорически запрещён txt2img в `end_image`! |

#### Практические правила для LTX-2.3 при использовании `end_image`:
1. **Категорический запрет чистого txt2img в `end_image`:**
   Если задать `end_image` через текстовый `prompt` без базового изображения, ракурс и композиция неизбежно разойдутся, и LTX выполнит монтажный скачок через шум на 2-й секунде.
2. **Использовать `"image_path": "$start"` с `denoise: 0.55–0.65`:**
   Целевой кадр обязан генерироваться через img2img строго относительно старта текущего блока. Это гарантирует 100% сохранение фоновой геометрии, освещения и анатомии, меняя лишь жест, мимику или предмет в руках.
3. **Сэмплер `euler_ancestral` вместо детерминированного `euler`:**
   Детерминированный сэмплер `euler` при наличии противоположных направляющих токенов вызывает жесткий ступор траектории и усугубляет рывок на 2-й секунде. Стохастический сэмплер `euler_ancestral` подмешивает шум на каждом шаге, позволяя модели плавно адаптировать фазы без визуального застывания.

## 14. Дефект 14: Рассинхронизация префикса LTX через внешние токены и прожиг LoRA в Wan-Fast при high-CFG

### Симптом:
1. **Wan 2.2 (`wan-fast`)**: При попытке задать `steps: 20..25` и `cfg: 5.0` на движке `wan-fast` с `overlap: 1.0` изображение моментально деградирует (прожиг цвета, кислотные артефакты, оплывание анатомии), а при переходе к следующим блокам ошибка катастрофически накапливается.
2. **LTX-2.3 (`ltx`)**: При генерации с `overlap: 1.0` видео на стыке полностью распадается: возникает резкий скачок движения, разрыв геометрии или провал в зашумлённую интерполяцию.

### Первопричины:
1. **Wan: Конфликт 4-шаговой Consistency LoRA с многошаговым Flow Matching сэмплингом:**
   - Движок `wan-fast` активирует дистиллированные LoRA (`wan2.2_i2v_lightx2v_4steps_lora_v1_high_noise` / `low_noise`), обученные исключительно на 4 шага с `CFG = 1.0`.
   - При 25 шагах с `CFG = 5.0` градиенты скорости умножаются пятикратно на каждом шаге. Латентная дисперсия экспоненциально растет ($\sigma > 3.5$), пробивая порог $|z| > 10.0$ и вызывая оверфлоу VAE декодера.
   - **Решение:** Внедрён автоматический защитный роутинг: если для `wan-fast` передаются параметры `steps > 8` или `cfg > 2.0`, пайплайн автоматически переключает исполнение на `WanFullVideoGenerator` (`wan-full`), который использует чистые High/Low Noise UNet без дистилляционных LoRA, штатно отрабатывая 20–25 шагов и CFG 5.0.

2. **LTX: Разница между Attention Reference Guide и In-Canvas Latent Prefix:**
   - Официальная нода ComfyUI `LTXVAddLatentGuide` конкатенирует латенты в конец списка токенов внимания (`latent_image = torch.cat([latent_image, guiding_latent], dim=2)`), оставляя кадры холста $0..k-1$ случайным белым шумом.
   - Пайплайн нарезки `slice_core` отрезал эти первые $k$ кадров, полагая, что они тождественны префиксу. Но ядро фактически начиналось с кадра, который уже 17 шагов генерировался вслепую от белого шума.
   - **Решение:** Разработана кастомная нода `LTXLatentPrefixToVideo` ([`ltx_latent_nodes.py`](file:///G:/Git/media_mcp/custom_nodes/ComfyUI-MediaMCP/ltx_latent_nodes.py)), реализующая честный Diffusion Forcing:
     - Латенты хвоста вшиваются прямо в холст: `samples[:, :, :k] = prefix_latent`.
     - Накладывается жесткая маска денойзинга: `noise_mask[:, :, :k] = 0.0` (заморозка префикса от белого шума).
     - После сэмплинга нода `LTXVAdainLatent` выравнивает цветовой баланс ядра по префиксу.
     - Нода `slice_core` срезает подлинный префикс, обеспечивая идеальный бесшовный стык без разрыва фазы.
